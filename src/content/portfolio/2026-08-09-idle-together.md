Idle Together는 작업하거나 공부하는 동안 작은 섬에 함께 머물며, 악기를 연주하고 그림으로 소통하는 멀티플레이어 데스크톱 컴패니언. 말없이 같은 공간에 있어도 서로의 행동을 느낄 수 있도록 만드는 프로젝트.

연주와 그림에서는 입력한 결과가 먼저 내 손에 맞춰 반응해야 함. 동시에 상대에게도 그 행동이 전달되어야 하므로, 로컬 반응과 네트워크 동기화를 분리해 구현했음. 연주는 현재 눌린 입력 상태를 갱신하고, 그림은 승인된 선분을 누적하는 방식으로 각 기능이 보존해야 할 정보를 구분.

## 연주: 지나간 입력보다 현재 상태를 전달

### 내 소리를 듣는 경로에서 네트워크 대기 제거

악기를 누른 뒤 Host의 응답을 받아 소리를 재생하면 연주자 자신의 입력에도 통신 지연이 붙음. `NetworkInstrumentPerformer`는 입력 즉시 로컬 악기를 재생하고, 해당 상태를 별도로 전송하도록 구성했음. 다른 Client의 소리는 Client → Host → Client 경로로 전달되지만, 내가 낸 소리를 듣는 데에는 이 경로의 응답을 기다리지 않음.

로컬 오디오 처리에서도 대기 시간을 줄이기 위해 씬 시작 전에 Unity 오디오 설정에 256 sample DSP buffer를 요청. 장치가 설정 변경을 거부하면 기존 구성을 유지하도록 처리했음. 이는 오디오 버퍼 크기에 대한 요청이며, 입력부터 실제 출력까지의 전체 지연을 보장하는 값은 아님.

### 누름과 뗌을 하나의 상태로 묶기

누름과 뗌 이벤트를 각각 보내는 구조에서는 뗌 메시지가 유실되면 상대에게 음이 계속 남을 수 있음. 반대로 과거 이벤트를 순서대로 재전송하면 이미 지나간 입력의 복구가 최신 연주의 전달을 늦출 수 있음. 현재 구현은 악기 종류, 연주 여부, 눌린 입력을 나타내는 비트 마스크를 한 패킷에 담아 전송.

양쪽 Client가 가진 악기 샘플을 각자 재생하므로 오디오 파형을 전송하지 않고도 원격 연주를 표현할 수 있음. Steam 전송 경로에서는 `UnreliableNoDelay`를 사용하고, 애플리케이션 패킷은 식별 정보와 순서 번호를 포함해 18바이트로 구성했음. 이 크기는 전송 계층의 헤더를 제외한 값.

입력이 바뀔 때 상태를 보내고, 연주 중에는 기본 0.05초 간격으로 전체 입력 상태를 다시 전송함. 뗌 상태가 담긴 패킷 하나를 놓쳐도 이후 snapshot에서 눌린 입력이 없다는 사실을 전달할 수 있는 구조. 수신 측은 이전 상태와 달라진 입력만 재생에 반영하고, 순서 번호로 중복되거나 뒤늦게 도착한 패킷을 걸러냄. 통신이 끊겨 최신 상태가 0.3초 동안 도착하지 않으면 원격 연주 상태를 만료시켜 음이 계속 남는 것을 막도록 구성했음.

이 방식이 보존하는 것은 현재 연주 상태. 누름과 뗌 사이의 패킷이 모두 유실된 짧은 음까지 복원하지는 못하며, 원격 연주의 도착 시간도 네트워크 상태에 따라 달라짐. 모든 음을 같은 시각에 재생하는 합주 동기화보다 최신 입력 상태를 빠르게 반영하는 데 초점을 둔 구현.

Host에서는 발신자가 해당 캐릭터의 소유자인지, 악기와 입력 슬롯이 유효한지 검사하고 재입력 간격을 적용한 뒤 다른 Client로 전달함. 로컬에서 먼저 반응하더라도 공유되는 상태의 검증은 Host에 유지했음.

## 그림: 손끝에는 즉시, 공유에는 선분 기록

### 그리기와 전송 주기를 분리

그림은 드래그하는 동안 선이 손끝을 따라와야 함. Host 승인 후에만 그리면 왕복 지연이 보이고, 입력 좌표가 바뀔 때마다 메시지를 보내면 드래그 빈도에 따라 전송 호출이 늘어남. Client에서는 선분을 캔버스에 먼저 그리고, 전송할 선분은 별도 목록에 모으도록 구현했음.

모인 선분은 기본 0.08초가 지나거나 32개가 쌓이면 Host로 전송. 드래그를 끝낼 때도 남은 선분을 즉시 보냄. 로컬 화면 갱신은 입력에 맞추고 네트워크 전송은 묶어서 처리하므로, 전송 주기를 기다리는 동안에도 그리는 사람의 선은 화면에 반영됨. 다른 사람에게 보이는 그림에는 이 배치 대기 시간이 추가되는 교환 관계가 있음.

### 픽셀 대신 그리는 명령을 공유

기본 캔버스인 256 × 192 RGBA32 텍스처는 압축 전 픽셀 데이터만 192 KiB. 변경 때마다 전체 이미지를 전달하는 대신, 시작점과 끝점의 좌표 4개를 `ushort`로 양자화하고 색상 인덱스, 반지름, 도구를 각각 `byte`로 표현했음. 선분 하나의 필드 데이터는 11바이트이며, 실제 메시지에는 RPC와 목록 동기화에 필요한 정보가 추가됨.

Host는 그리기 권한, 색상과 반지름 범위, Client별 입력 빈도를 검사한 뒤 선분을 Server 쓰기 권한의 `NetworkList`에 추가. 각 Client는 이 기록을 캔버스에 적용하고, 뒤늦게 참가한 Client도 누적된 선분을 재생해 그림을 구성하도록 연결했음. 현재 화면을 만드는 명령이 공유 기록으로 남기 때문에 입장 시점이 달라도 같은 그림을 복원하는 데 사용할 수 있음.

연주는 최신 상태가 과거 상태를 대체하지만, 그림은 이전 선분이 빠지면 결과 자체가 달라짐. 이 차이에 맞춰 연주는 상태 snapshot, 그림은 순서가 있는 누적 기록을 사용했음.

## 확인 범위와 남은 작업

소스에서 로컬 선반영, 연주 상태 패킷과 주기 전송, Host 검증, 그림 배치 전송과 기록 재생 경로를 확인. Edit Mode 테스트에는 잘못된 패킷 형식 거부와 순서 번호의 중복, 역전, 순환 판별, 그림 좌표 양자화와 권한 규칙 검사가 포함되어 있음. 일부 연결 검사는 소스와 직렬화 설정을 대상으로 하므로 실제 두 Client 사이의 통신 검증과는 범위가 다름.

현재 문서에서 확인한 근거는 구현 코드와 테스트 정의까지이며, 해당 테스트의 실행 결과와 원격 오디오 지연 측정값은 확보하지 않았음. 패킷 유실 환경에서의 짧은 음 누락, 실제 출력 지연과 공동 그림의 일치 여부는 두 Client로 검증할 항목.

그림에는 최대 8,192개 선분 제한이 있으며 이후 입력을 계속 받기 위한 기록 압축은 미구현. Host가 거절한 선분도 로컬에는 먼저 그려질 수 있어 승인된 기록을 기준으로 화면을 되돌리는 보정이 남아 있음. 장시간 공동 작업을 지원하려면 기록 크기 관리와 로컬 화면의 재조정을 함께 해결해야 함.
