## 각자 할 일을 하면서, 같은 공간에 머무는 게임

계속 대화하거나 무언가를 함께 달성하지 않아도, 옆에 누군가 있다는 느낌을 주고 싶습니다. 평소에는 빗소리나 바람 소리, Lo-fi 음악을 들으며 각자의 일을 하고, 잠깐 쉬고 싶을 때 악기를 연주하거나 같은 캔버스에 그림을 그리는 공간입니다.

이런 작은 상호작용일수록 반응이 자연스러워야 한다고 생각했습니다. 입력한 뒤 한참 지나서 소리가 나거나, 옆 사람이 그린 선이 내 화면에만 없다면 함께 있다는 감각이 끊어집니다.

- 내 연주와 그림은 입력 직후 내 화면과 소리에 반영
- 상대에게는 연주한 순서와 음 사이의 간격을 전달
- 늦게 들어온 사람도 지금 함께 그리고 있는 그림에서 시작

## 악기마다 통신 코드를 다시 쓰지 않는 프레임워크

악기가 바뀌어도 입력을 받고, 다른 사람에게 전달하고, 재생하는 흐름은 같습니다. 이 공통 흐름과 악기별 소리 내는 규칙을 분리했습니다. 새 악기를 추가할 때 음원과 입력 해석을 연결하면 기존 전송 경로를 함께 사용할 수 있는 구조입니다.

| 구성 요소 | 맡은 역할 |
| --- | --- |
| `InstrumentDefinition` | 음원, 재생 규칙, 프리팹의 AudioSource와 시각 표현 정의 |
| `NetworkInstrumentPerformer` | 입력 슬롯 관리, 로컬 반영, Host 검증과 원격 상태 적용 |
| `InstrumentRealtimeProtocol` | 공통 입력 상태를 26바이트로 직렬화하고 수신 데이터 검사 |
| `IInstrumentRealtimeTransport` | 악기 로직과 실제 전송 경로 연결 |
| `InstrumentPlaybackBuffer` | 받은 상태를 연주 시각에 맞춰 꺼내기 |

전송 계층은 ‘이 입력이 어떤 음인가’를 알 필요가 없습니다. 최대 8개 슬롯의 눌림 상태를 보내면 악기 정의가 여러 음을 함께 낼지, 마지막 입력만 재생할지, 여러 입력의 조합으로 음높이를 결정할지 해석합니다.

- 음원, 누르는 동안 반복할지 여부, 놓았을 때의 소리와 음량 변화는 악기 데이터로 지정
- 소리와 화면 표시는 프리팹에 연결하고, 런타임에서는 준비된 AudioSource와 표시 상태 갱신
- 악기 전환 시 이전 음과 입력 상태를 정리하고 새 악기 정의로 교체
- 같은 전송 형식을 쓰기 위해 참가자마다 같은 순서의 악기 카탈로그 사용

현재 실제 카탈로그에는 오카리나 1종이 연결되어 있습니다. 프레임워크의 여러 재생 방식은 테스트했지만, 새 악기의 음원과 프리팹까지 모두 준비한 상태는 아닙니다.

## SYNCROOM을 참고해 정한 전송 기준

Yamaha의 **SYNCROOM**은 실제 오디오를 주고받고, 회선 상태에 맞춰 버퍼를 조절해 지연과 끊김을 다룹니다. 여기서 참고한 것은 ‘빨리 전달하기’와 ‘입력 사이의 간격 유지하기’를 함께 봐야 한다는 점입니다. [Yamaha 기술 소개](https://syncroom.yamaha.com/about/)

Idle Together에서는 각 PC가 게임에 포함된 음원을 재생합니다. 따라서 오디오 스트림 대신 **누가, 어떤 악기의 입력을, 언제 바꿨는지** 전달하도록 설계했습니다.

- 내 입력은 통신을 기다리지 않고 로컬에서 즉시 반영
- Host가 송신자와 입력을 검사한 뒤 다른 참가자에게 중계
- 상대는 패킷 도착 시각보다 원래 입력 시각을 기준으로 상태 적용

SYNCROOM은 참가자 PC 사이에서 오디오를 직접 주고받지만, 현재 게임은 Host를 거칩니다. 회선에 따라 자동으로 버퍼를 조절하는 기능도 아직 없습니다. SYNCROOM의 내부 프로토콜을 재현한 것은 아니며, 공개된 동작을 기준으로 게임에 필요한 전송 구조를 설계했습니다. [SYNCROOM 공식 FAQ](https://syncroom.yamaha.com/v2/play/faq/index_pc.html)

## 버튼 하나에서 시작하는 패킷 전달

입력 슬롯 하나가 바뀌면 로컬에서는 바로 반영하고, 네트워크에는 현재 상태를 담은 패킷을 보냅니다. 아래 시각화에서는 같은 입력이 Host를 거쳐 가까운 참가자와 먼 참가자에게 전달되는 과정을 볼 수 있습니다.

경로가 길어지거나 회선이 혼잡하면 도착이 늦어질 수 있습니다. 다만 거리만으로 실제 지연을 계산할 수는 없어, 여기서는 **경로별 지연을 직접 설정하는 모형**으로 표현했습니다. 게임 속 캐릭터 간 거리에 따라 패킷을 선별하는 기능을 뜻하지는 않습니다.

## 26바이트 raw 패킷을 직접 정의

악기 입력에 필요한 값을 고정 크기 바이너리 형식으로 정의했습니다. `InstrumentRealtimeProtocol`에서 필드의 위치와 바이트 순서를 직접 지정하고, 쓰기와 읽기가 같은 규약을 따르도록 구현했습니다.

| Offset | 크기 | 필드 | 설계 기준 |
| --- | --- | --- | --- |
| 0 | 4B | Magic `ITM1` | 일반 Netcode 메시지와 악기 패킷 식별 |
| 4 | 1B | Version | 현재 v2, 다른 버전의 잘못된 해석 방지 |
| 5 | 1B | Flags | bit 0에 연주 중 여부, 나머지는 예약 |
| 6 | 2B | Sequence | 중복과 이전 입력 판별 |
| 8 | 8B | NetworkObjectId | 입력이 속한 객체 식별 |
| 16 | 1B | InstrumentIndex | 공통 카탈로그에서 악기 선택 |
| 17 | 1B | PressedMask | 8개 입력 슬롯을 비트 단위로 표현 |
| 18 | 8B | ServerTime | 입력 당시의 공통 시각 기록 |

- 정수는 **little-endian**, 시각은 IEEE 754 `double`의 비트 표현으로 기록
- 구조체 메모리를 통째로 복사하지 않고 필드마다 기록해 패딩과 메모리 배치에 의존하지 않는 형식 사용
- Steam의 수신 포인터와 일반 `ArraySegment<byte>` 양쪽에서 같은 형식 해석
- 배열 조각을 읽을 때 시작 오프셋을 반영하고, 읽기 전에 본문 길이가 정확히 26바이트인지 검사

이 26바이트는 직접 정의한 **애플리케이션 메시지 본문**입니다. Steam, RPC와 IP 등의 헤더나 암호화 비용까지 포함한 전체 네트워크 패킷 크기는 아닙니다.

### Steam 전용 경로와 RPC가 같은 본문 사용

Steam 연결에서는 직렬화한 바이트를 `SteamNetworkingSocketsTransport`에 직접 넘깁니다. 수신 시 Magic으로 악기 메시지를 구분하고, 전용 디코더를 거쳐 performer에 전달합니다. 연결된 악기 전용 transport를 사용할 수 없으면 같은 26바이트를 reliable RPC에 담습니다.

- Steam에서는 `ReliableNoNagle`로 전송해 작은 메시지를 모아 보내기 위한 Nagle 대기를 생략
- 일반 Netcode 연결에서는 `byte[]` 본문을 RPC로 전달하고 같은 디코더와 Host 검증 사용
- 패킷 형식과 악기별 로직을 유지한 채 전송 경로만 교체

재전송과 전달 순서는 Steam/Netcode의 reliable 전송 계층에 맡겼습니다. 직접 구현한 부분은 그 위의 바이너리 형식, 입력 검증과 재생 상태 관리입니다. `ReliableNoNagle`도 회선 지연이나 재전송 대기까지 없애지는 않습니다.

### 읽을 수 있는 패킷과 받아들일 입력 구분

형식이 맞는 패킷이라도 다른 플레이어의 객체를 조작하거나 이미 지난 입력을 다시 적용하게 두어서는 안 됩니다. 디코더의 형식 검사와 Host의 게임 규칙 검사를 나눴습니다.

1. **디코더:** 길이, Magic, 버전, 예약 플래그와 유효한 시각 검사
2. **Host:** 연결에서 확인한 송신자가 해당 객체의 소유자인지 검사
3. **입력:** 악기 카탈로그 범위와 사용 가능한 슬롯 확인, 너무 빠른 반복 입력 제한
4. **순서와 시각:** 중복/이전 순서, 뒤로 가는 시각, 지나치게 오래되거나 미래인 입력 제외

순서 번호는 16비트이므로 65,535 다음에 0으로 돌아갑니다. 숫자의 대소만 비교하지 않고 `(새 번호 - 이전 번호) mod 65536`이 1~32,767인지 검사해 순환 구간을 처리합니다. 반주기 이상 떨어진 번호는 새 입력으로 판단하지 않습니다.

Host는 허용되지 않은 슬롯을 제거하고, 연주 시각을 기준으로 같은 슬롯의 반복 입력을 제한합니다. 기본 제한은 슬롯당 35ms, 플레이어당 초당 160패킷입니다. 시각은 Host 기준 100ms 넘는 미래 또는 1초 넘는 과거라면 거부합니다.

### 상태와 순서를 함께 보내는 이유

각 패킷은 현재 눌린 슬롯 전체를 담지만, 입력이 바뀌는 순간마다 전송합니다. 최신 상태만 남기면 ‘누름 → 놓음 → 누름’ 사이의 동작이 사라질 수 있기 때문입니다.

- 입력 변경 시 즉시 전송하고, 연주 중에는 50ms마다 현재 상태를 다시 전송
- 모든 메시지에 새 순서 번호 부여, 중복 수신은 제외
- 이전 마스크와 새 마스크의 XOR로 바뀐 슬롯을 찾아 누름과 놓음 적용
- 통신이 끊기면 재생 중인 음과 대기열을 비우되, 마지막 순서 번호는 유지해 오래된 패킷이 음을 다시 켜는 상황 방지

## 도착과 재생을 분리한 버퍼

전송 순서가 맞아도 도착 간격은 흔들릴 수 있습니다. 받은 상태를 즉시 전부 적용하지 않고, `ServerTime + 80ms`를 기본 재생 기준으로 사용합니다. 공통 시계는 Netcode의 `ServerTime`이며, Host는 중계할 때 원래 입력 시각을 유지합니다.

- 플레이어별 대기열에 최대 128개 상태 보관
- 늦은 입력이 묶여 도착하면 이후 재생 시각을 뒤로 옮겨 입력 사이의 간격 유지
- Unity 프레임이 늦어져 여러 입력을 한 번에 처리하게 되는 경우에도 누름과 놓음을 구분하도록 남은 재생 시각 조정

버퍼는 지연을 없애는 기능이 아닙니다. 늦은 입력을 기다리면 전체 연주도 늦어지고, reliable 재전송 중에는 뒤의 입력도 함께 기다릴 수 있습니다. 현재는 고정 버퍼와 Update 단위 재생이며, 자동 버퍼 조절과 오디오 샘플 단위 예약 재생은 아직 구현하지 않았습니다.


## 함께 그리기: 내 손에는 바로, 모두의 화면에는 같은 그림

그림도 같은 기준으로 만들었습니다. 내 손이 움직일 때 선은 바로 보여야 하고, 다른 사람과 함께 그린 결과는 서로 같아야 합니다.

- **그리는 동안:** 내 화면에 선을 먼저 표시하고 짧은 묶음으로 Host에 전송
- **공유할 때:** Host가 권한과 입력값을 검사하고, 받아들인 선을 참가자에게 전달
- **응답을 받으면:** Host가 확정한 그림 위에 아직 응답받지 못한 내 선만 겹쳐 표시

손님에게 그리기 권한이 없거나 너무 많은 입력을 보내 선이 거절되면, 그 선은 내 화면에서도 지웁니다. 동시에 그린 선이 겹치는 순서는 Host가 받은 뒤 확정한 순서를 따릅니다.

늦게 들어온 사람에게는 처음부터 모든 선을 다시 보내지 않습니다. **현재 그림을 압축해 전달**하므로, 얼마나 오래 그렸든 지금의 캔버스에서 함께 시작할 수 있습니다.

- 평소에는 시작점과 끝점, 색상, 굵기와 도구를 담은 11바이트 선분 전송
- 참가하거나 그림이 어긋났을 때는 현재 픽셀 데이터를 Deflate로 압축해 나누어 전달
- 기본 캔버스는 256 × 192, 압축 전 48 KiB
- 자유롭게 그리는 붓 외에 Shift+드래그 직선 도구 제공

직선 도구의 조작은 Rust의 [Painting Line Tool](https://rust.facepunch.com/news/shipshape)을 참고했습니다. 현재 그림 공유는 같은 세션 안에서 동작하며, 디스크 저장과 실행 취소는 아직 구현하지 않았습니다.

## 현재 확인한 범위

2026년 9월 7일 기록 기준, Unity 6000.6.0f1에서 관련 테스트 **39개 통과**를 확인했습니다.

- 짧게 누른 음, 같은 음을 연속으로 누른 입력, 늦게 묶여 도착한 입력의 처리
- 프레임이 늦어져도 누르고 놓는 과정이 한 번에 사라지지 않는 동작

- 실제 loopback 연결에서 그림 공유, 거절된 선의 제거와 늦은 참가자의 그림 복원

통신 테스트는 한 PC 안의 Host와 Guest를 연결해 진행했습니다. 서로 다른 PC의 Steam 회선에서 빠른 곡을 함께 연주하는 품질은 더 확인해야 합니다. 특히 입력부터 상대의 소리가 나오기까지의 지연과, 그림을 전송하는 동안 연주가 얼마나 영향을 받는지는 실제 환경에서 측정할 과제로 남아 있습니다.
