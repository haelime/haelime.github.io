## 각자 할 일을 하면서, 같은 공간에 머무는 게임

계속 대화하거나 무언가를 함께 달성하지 않아도, 옆에 누군가 있다는 느낌을 주고 싶습니다. 평소에는 빗소리나 바람 소리, Lo-fi 음악을 들으며 각자의 일을 하고, 잠깐 쉬고 싶을 때 악기를 연주하거나 같은 캔버스에 그림을 그리는 공간입니다.

이런 작은 상호작용일수록 반응이 자연스러워야 한다고 생각했습니다. 건반을 눌렀는데 한참 뒤에 소리가 나거나, 옆 사람이 그린 선이 내 화면에만 없다면 함께 있다는 감각이 끊어집니다.

- 내 연주와 그림은 입력 직후 내 화면과 소리에 반영
- 상대에게는 연주한 순서와 음 사이의 간격을 전달
- 늦게 들어온 사람도 지금 함께 그리고 있는 그림에서 시작

## SYNCROOM에서 참고한 것: 빠른 전달과 일정한 리듬

합주 기능의 레퍼런스는 Yamaha의 **SYNCROOM**입니다. 실제 오디오를 작은 지연으로 주고받고, 회선 상태에 맞춰 수신 버퍼를 조절해 소리가 끊기거나 간격이 흔들리는 문제를 다룹니다. [Yamaha 기술 소개](https://syncroom.yamaha.com/about/)

참고한 핵심은 ‘빨리 도착하는 것’과 ‘일정한 간격으로 들리는 것’을 함께 봐야 한다는 점입니다. Idle Together에서는 게임 안에 준비된 악기 음원을 각자의 PC에서 재생하므로, 전송할 정보를 다르게 잡았습니다.

| 구분 | SYNCROOM | Idle Together의 현재 구현 |
| --- | --- | --- |
| 주고받는 정보 | 실제 연주한 오디오 | 악기 종류, 누른 키의 상태와 연주 시각 |
| 전달 경로 | 참가자 PC 사이의 직접 오디오 통신 | 연주자 → Host → 다른 참가자 |
| 도착 시간의 흔들림 처리 | 회선 상태를 살피며 버퍼 조절 | 정해 둔 시간만큼 기다린 뒤 연주 시각에 맞춰 반영 |

SYNCROOM의 통신 경로와 버퍼 동작은 [공식 FAQ](https://syncroom.yamaha.com/v2/play/faq/index_pc.html)를 참고했습니다. 내부 프로토콜을 그대로 옮긴 것은 아니며, 현재 구현의 합주 품질이 SYNCROOM과 같다는 의미도 아닙니다.

## 피아노로 풀어 보는 연주 프로토콜

피아노에서 ‘도’를 두 번 누르는 상황을 생각하면 이해하기 쉽습니다. 상대에게 필요한 정보는 마지막에 도가 눌려 있다는 사실뿐 아니라, **한 번 누르고, 놓고, 다시 눌렀다는 과정**입니다.

아래는 그 과정을 보여 주는 Three.js 시각화입니다. 회선의 지연을 바꾸며 도착 즉시 반영하는 방식과 잠깐 기다리는 방식을 비교할 수 있습니다. 피아노는 설명용 예시이며, 현재 게임 카탈로그에 연결된 악기는 오카리나 1종입니다.

### 내 소리는 바로, 상대의 소리는 연주 시각에 맞춰

내가 누른 건반까지 Host의 응답을 기다릴 필요는 없습니다. 내 PC에서는 바로 소리를 내고, 공유할 입력은 별도로 보냅니다.

1. **연주자:** 키를 누르거나 놓으면 로컬 악기 재생 상태를 즉시 변경
2. **전송:** 누른 키의 상태, 악기 번호, 순서 번호와 공통 시계 기준의 연주 시각을 전달
3. **Host:** 해당 플레이어의 입력인지, 악기와 입력값이 유효한지 검사한 뒤 원래 연주 시각을 유지해 중계
4. **상대방:** 입력을 잠깐 보관하고 `연주 시각 + 재생 버퍼`에 맞춰 자신의 악기 음원 재생

공통 시계는 Netcode의 `ServerTime`을 사용합니다. 서로 다른 PC의 로컬 시각을 그대로 비교하지 않도록 하기 위한 기준입니다.

현재 패킷 본문은 **26바이트**입니다. 입력이 바뀔 때 즉시 보내고, 연주 중에는 50ms마다 현재 상태를 다시 보내 지금 누른 키도 확인할 수 있게 했습니다. 이 크기에는 RPC와 통신 헤더가 포함되지 않습니다.

### 같은 음을 두 번 누르면, 상대에게도 두 번 들리도록

처음에는 가장 최근의 눌림 상태만 보내고, 중간에 잃어버린 패킷은 다시 보내지 않았습니다. 하지만 ‘누름 → 놓음 → 누름’에서 가운데 정보가 빠지면 상대는 건반을 계속 누르고 있었다고 받아들이게 됩니다. 짧게 눌렀다가 놓은 음은 통째로 빠질 수도 있습니다.

- 키를 누르고 놓을 때마다 상태를 전송하고, 전송 계층에서 누락된 패킷 재전송과 순서 보장
- Steam에서는 `ReliableNoNagle`, 그 외 Netcode 연결에서는 reliable RPC 사용
- 중복되거나 이전 순서의 패킷은 제외하고, 통신이 끊기면 계속 울리는 음과 대기 중인 입력 정리

테스트에서는 패킷을 모두 받아도 두 번 누른 음이 하나처럼 처리되는 문제를 발견했습니다. Unity의 한 프레임이 늦어지면서 ‘누름, 놓음, 다시 누름’을 같은 Update 안에서 전부 처리한 것이 원인이었습니다. 서로 다른 시각의 입력이 한꺼번에 밀리면, 뒤의 입력을 조금 늦춰 각각의 동작이 드러나게 수정했습니다.

### 조금 기다리는 이유와 그 대가

일정한 간격으로 연주해도 패킷은 들쭉날쭉 도착합니다. 도착하자마자 재생하면 그 흔들림이 음 사이의 간격으로 옮겨 갑니다.

- 상대의 연주는 기본 **80ms 버퍼**를 두고, 도착 시각보다 원래 연주 시각을 기준으로 처리
- 설정 범위는 20~200ms, 내 입력에는 이 대기 시간을 추가하지 않는 방식
- 이미 늦은 입력이 묶여 도착하면 남은 입력의 재생 시각도 뒤로 옮겨 누르고 놓는 간격 유지

버퍼보다 늦게 도착한 음을 제시간에 돌려놓을 수는 없습니다. 패킷을 다시 받는 동안 뒤의 음도 기다릴 수 있고, 프레임이 늦어지면 음 사이의 간격이 더 늘어날 수 있습니다. **80ms는 설정값이며 실제로 상대의 스피커에서 소리가 나기까지 걸리는 전체 지연은 아닙니다.**

SYNCROOM처럼 회선에 따라 버퍼를 자동으로 조절하거나 오디오 샘플 단위로 재생을 예약하는 단계까지는 구현하지 않았습니다. 현재는 누른 순서와 짧은 음을 놓치지 않는 전송 구조를 마련한 상태입니다.

### 악기가 늘어나도 전송 방식은 함께 사용

전송하는 입력과 악기가 소리를 내는 규칙을 분리했습니다. 같은 입력 상태를 받아도 여러 음을 함께 낼지, 마지막에 누른 음만 낼지는 악기 쪽에서 결정합니다.

- 여러 키를 함께 누르면 여러 음을 재생하는 방식 지원
- 한 음만 내는 악기는 마지막에 누른 키를 우선하고, 놓으면 아직 누르고 있는 이전 키로 복귀
- 오카리나는 구멍과 숨 입력의 조합으로 음높이 결정

현재는 최대 8개 입력 슬롯을 공유하는 구조입니다. 여러 음을 함께 내는 동작은 테스트했지만, 88건반과 건반을 누르는 세기, 페달까지 표현하는 피아노 프로토콜은 아닙니다. 새 악기를 넣으려면 음원, 프리팹과 UI 연결도 추가해야 합니다.

## 함께 그리기: 내 손에는 바로, 모두의 화면에는 같은 그림

그림도 같은 기준으로 만들었습니다. 내 손이 움직일 때 선은 바로 보여야 하고, 다른 사람과 함께 그린 결과는 서로 같아야 합니다.

- **그리는 동안:** 내 화면에 선을 먼저 표시하고 짧은 묶음으로 Host에 전송
- **공유할 때:** Host가 권한과 입력값을 검사하고, 받아들인 선을 참가자에게 전달
- **응답을 받으면:** Host가 확정한 그림 위에 아직 응답받지 못한 내 선만 겹쳐 표시

손님에게 그리기 권한이 없거나 너무 많은 입력을 보내 선이 거절되면, 그 선은 내 화면에서도 지웁니다. 동시에 그린 선이 겹치는 순서는 Host가 받은 뒤 확정한 순서를 따릅니다.

늦게 들어온 사람에게는 처음부터 모든 선을 다시 보내지 않습니다. **현재 그림을 압축해 전달**하므로, 얼마나 오래 그렸든 지금의 캔버스에서 함께 시작할 수 있습니다.

- 평소에는 시작점과 끝점, 색상, 굵기와 도구를 담은 11바이트 선분 전송
- 참가하거나 그림이 어긋났을 때는 현재 픽셀 데이터를 Deflate로 압축해 나누어 전달
- 기본 캔버스는 256 × 192, 압축 전 48 KiB
- 자유롭게 그리는 붓 외에 Shift+드래그 직선 도구 제공

직선 도구의 조작은 Rust의 [Painting Line Tool](https://rust.facepunch.com/news/shipshape)을 참고했습니다. 현재 그림 공유는 같은 세션 안에서 동작하며, 디스크 저장과 실행 취소는 아직 구현하지 않았습니다.

## 현재 확인한 범위

2026년 9월 7일 기록 기준, Unity 6000.6.0f1에서 관련 테스트 **39개 통과**를 확인했습니다.

- 짧게 누른 음, 같은 음을 연속으로 누른 입력, 늦게 묶여 도착한 입력의 처리
- 프레임이 늦어져도 누르고 놓는 과정이 한 번에 사라지지 않는 동작
- 여러 음을 함께 내는 방식, 한 음만 내는 방식과 오카리나 입력 처리
- 9,000회 그린 그림의 압축과 복원 결과 일치
- 실제 loopback 연결에서 그림 공유, 거절된 선의 제거와 늦은 참가자의 그림 복원

통신 테스트는 한 PC 안의 Host와 Guest를 연결해 진행했습니다. 서로 다른 PC의 Steam 회선에서 빠른 곡을 함께 연주하는 품질은 더 확인해야 합니다. 특히 입력부터 상대의 소리가 나오기까지의 지연과, 그림을 전송하는 동안 연주가 얼마나 영향을 받는지는 실제 환경에서 측정할 과제로 남아 있습니다.
